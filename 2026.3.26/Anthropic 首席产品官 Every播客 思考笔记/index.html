    思考笔记

    标题：Anthropic 首席产品官的产品哲学，推荐所有非技术背景的产品经理和vibe coders

    Dan Shipper 的播客昨天请到了 Anthropic 现任首席产品官、Instagram 联创 Mike Krieger ，讲了很多反常识的观点，推荐给非技术背景、正努力转型成为 AI 产品经理，或者沉迷于 vibe coding 的各位～

    作为一个"自降身份"，去到 Anthropic 内部实验室负责孵化不同产品的首席产品官，Krieger 对当前这波 vibe coding 浪潮下如何打造一款 agent-native 的好产品可以说见解十分深刻了。

    比如他说，现在 AI 让做出一款产品的速度大大加快，但这也是真正爆发的好产品并不多的原因所在。

    我没有经历过打造一款产品的完整过程，但最近在搭各种 skill。节目里很多观点，对我也很有启发。

    下面是我的一些 takeaways 和感受：

    ==1. vibe coding 时代最大的陷阱是"建得太快太多"== 在 Anthropic 这段时间，Krieger 说他一直在思考一个问题：当 AI 把做产品这件事变得更快、更简单之后，什么才是最本质的东西？哪些事并没有变得更容易。

    他发现很多时候，当人们在做一款产品的时候，都会把它搞得很复杂。但是你要判断什么该删掉，则需要大量真实的使用经验，这是一个不断迭代的过程。

    更重要的是，关于什么东西应该放进去的直觉，你究竟想用这个产品怎么去影响世界的这种判断，是需要时间去积累的。不是花几个小时 vibe coding 就能有的。

    Krieger 举了一个例子。在做出 Instagram 前，他们团队还做过一款产品叫 Bourbon，但它是个失败品。

    而从 Bourbon 到 Instagram，他们做了非常多微小的、很凭直觉的决策。如果没有这个过程，Instagram 可能也不会如此成功。

    最近搭 skill 也有一个很深刻的体会：不要奢望别人搭出来的，或你一开始搭出来的这个 skill 就非常完美。

    它一定是越迭代越好用。最初的版本势必有各种小问题，小到什么时候执行，输出结果的格式，很多跟你的使用需求相关。你就要结合这些问题，逐个解决、逐步优化。

    ==2. 产品越早发布，可能越有好处== 当然，"不要建得太快太多"不等于"准备好再行动"。

    Krieger 有个很发直觉的观点：做一款新产品，要先建得简单，然后尽快发布。

    可能我们很多时候都会觉得，你做一款产品，一定要把它打磨得足够可靠、足够好、足够完美了才能上线。

    但他认为，如果你发现了一个问题，最好赶紧用最简单的方式（比如10天）做出一个 V1 版本来解决这个问题，之后再用更长的时间迭代。

    他拿 Anthropic 自己的产品 Co-work 举例。他们其实酝酿这个产品方向很久了，但真正决定动手做的时候，只给了自己 10 天，做了一个最小版本就发出去了。

    V1 有一百个想加没加的东西。发布之后他们很快发现，用户真正在乎的是他们之前完全没预料到的另外一些事。

    如果多花两个月先打磨出一个"完美"版本，大概率是在打磨一棵室内种出来的树——看着枝叶齐全，但一碰真实世界的风，就知道不对了。

    ==3. Agent-native 不是功能列表，而是一种设计原则== 这个观点我觉得也很有价值。

    Krieger 理解的agent-native 产品，并不仅仅只是"支持 API"或者"有一个 agent 模式"。

    他拿 Anthropic 的两款产品做对比，Claude AI 和 Claude Code。

    Claude AI 就是大家平时用的网页版聊天助手，2024 年推出，主要是对话交互。Claude Code 则是 2025 年推出的编程工具，可以直接在你的电脑上执行操作、读写文件、跑代码，是一个真正在帮你"做事"的工具。

    在他看来，Claude Code 做到了 agent-native，Claude AI 并没有。

    功能不够强大只是表面，更重要的是 Claude AI 从设计之初就没有把 agent-native 当成原则。

    他举了个例子：有人让 Claude AI 把一个文档直接加进项目知识库，回答是"我来告诉你手动操作的步骤"。

    这就很说明问题。产品原生能做的动作，现在却让用户去操作。后来再打补丁，也补不回设计上的缺口。

    Claude Code 就不一样。它对自己的机制有了解，可以自己查 skill 目录、自己安装、判断是否需要重启，

    所以 agent-native 不是一个可以后来"加上去"的功能，而是从第一天就要贯穿进去的设计哲学。

    ==4. 启动一个新产品的最低门槛：至少有一个人抱着"要么做死，要么成功"的信念==

    Krieger 提到，他们在实验室内部开发新产品的团队往往极其精简。他认为过度、过早的扩张是一件坏事，因为会有更多时间花在对齐上。

    但更重要的是，他们怎么判断要不要启动一个新项目。

    最低的门槛是，这个小团队里至少有一个 key player，抱着"要么做死，要么成功"的信念。

    他说，内部每次复盘被砍掉的项目，几乎都是同一个结论：团队里没有一个人是真正相信这件事的。大家只是觉得"还行吧"。那就是死亡判决。

    这个"有信念的人"，可能是设计师，也可能是有产品思维的工程师。但他们发现，几乎不会是 PM。他们整个 labs 里面只有一个 PM。

    因为团队精简，开发速度也非常快。实验室内部每两周会评估一次每个项目，决定是加注，还是把项目里的人释放回更大的人才池。流动性非常强，没有人会被永久固定在一个项目上。

    听完这期播客，一个最深刻的感受就是，当下 AI 只是把执行速度加快了，但人的判断力，所谓直觉才是关键。

    什么该留、什么该删、要不要相信这件事，这些还是需要时间、经历和真实世界的摩擦才能长出来的。

    这么看的话，对于非技术背景、想进入 AI 产品行业的人来说，当下恐怕是最好的时代。前提是你仍珍视自己的思想，怀有跟这个真实世界不断交互的热忱。
